# Small Worlds 渲染器可读性重构设计

状态：已按当前实现静态审核，待实施验证  
范围：Vite + TypeScript 应用中的原生 Canvas 体素渲染器  
依据：当前 `src/main.ts`、`src/renderer.ts`、`index.html`、`package.json` 和 `tsconfig.json`；`original.html` 仅作历史追溯

## 1. 背景与问题

`src/renderer.ts` 将数学与随机查表、场景数据、材质、体素构建、动态覆盖、像素渲染、画面内 UI 和五个场景放在同一模块中。场景通过模块级变量隐式使用当前场景，切换与恢复顺序影响最终画面。文件顶部使用 `@ts-nocheck`，因此即使项目开启严格类型检查，核心实现仍缺乏类型保障。

本设计解决的是可理解性、可维护性和可验证性，不改变产品视觉设计或交互功能。

## 2. 目标与非目标

### 目标

- 将场景定义、共享渲染能力、画面内 UI 和应用交互拆分为职责明确的模块。
- 将场景依赖和可变状态的所有权显式化，减少跨模块隐式读写。
- 保留五个场景及其顺序、体素算法、动画、像素风格、键盘和滑块行为。
- 建立可重复的图像回归与交互检查，在每次迁移后比较行为。
- 新模块启用 TypeScript 严格检查，并最终逐步移除渲染器中的 `@ts-nocheck`。
- 保留原始附件以便追溯；不依赖 LeaferJS 或其他图形引擎。

### 非目标

- 重写体素算法、调整光照或美术效果、增加场景或编辑功能。
- 改变 Canvas 尺寸与缩放策略、动画时长、场景切换逻辑或现有无障碍标签。
- 为多画布、异步渲染、Web Worker 或并行场景提供支持。
- 在没有测量证据时做性能优化，或将性能指标凭空设为固定阈值。

## 3. 现有行为与风险

一次实际重绘的调用链为（暂停且未标记 dirty 的动画帧不绘制）：应用入口按播放时间选择场景和进度；渲染器恢复上一帧动态体素，必要时懒构建场景；重置现有帧状态并执行场景更新；刷新调色板、渲染体素并绘制后处理；执行平移淡出、整数缩放和画面内 UI；最后通过 `putImageData` 提交 Canvas。

关键约束：

- `useScene` 将场景数组与缓存切换到模块级别名；材质数、色阶数和静态高度为标量副本，需要 `saveCounts` 写回。帧更新中也可能分配材质，不能只在构建后保存。
- 动态覆盖日志记录体素的原值，必须对所属场景按逆序恢复；切场景不能把旧日志应用到新场景。
- 各场景的闭包数据在 build、update 和 post 间持续存在；注册顺序影响数字键、方向键和标题。
- 帧缓冲区和部分帧状态全局复用，重构不应假设渲染可重入，也不能无意改变原有部分字段的重置规则。
- 位运算、数组类型、取整、调色板刷新和后处理顺序均是视觉兼容性的一部分。

## 4. 总体设计

按依赖方向分层，分阶段实现；以下是目标职责而不是要求一次性创建的文件清单：

```text
main.ts：Canvas 生命周期、时间、键盘和指针
    ↓
renderer/index.ts：对应用提供稳定的单实例门面
    ├─ renderer/context.ts：活动场景、帧状态和缓冲区的所有权
    ├─ renderer/geometry.ts：体素构建与动态写入
    ├─ renderer/materials.ts：材质、色阶和调色板
    ├─ renderer/voxel-renderer.ts：投影、光照及像素渲染
    ├─ renderer/effects.ts：动态覆盖日志、后处理和淡入淡出
    ├─ scenes/：场景契约、五个场景和显式注册顺序
    ├─ ui/：画面内字体、标题、滑块和整数缩放
    └─ core/：数学、确定性噪声、常量和查表
```

上图是职责分组，不表示所有箭头均为运行时 import：组合根创建上下文、基础能力和场景并注入依赖；`scenes/` 只依赖独立契约和注入的能力，不能反向导入注册表或门面。几何与动态写入共享的低层能力应由组合根装配，避免通过互相 import 或上下文中隐式服务定位形成环。模块路径须避免 `renderer.ts` 与 `renderer/index.ts` 的扩展名省略解析歧义：迁移期间明确采用唯一入口路径，切换后再删除旧入口。保留兼容门面，使 `main.ts` 在各阶段不需要同步大改。

### 4.1 渲染上下文

`RendererContext` 是单个渲染器的内部状态容器，逻辑上包含：

- 场景运行数据：活动场景、体素数组、材质数组、缓存与计数器。
- 帧状态：场景时间、光照、色彩分级和其他现有帧参数。
- 工作缓冲：逻辑分辨率像素、深度及其他辅助缓冲、复用的偏移缓冲。
- 动态覆盖：修改日志、当前条目数、动态高度与所属场景。

明确所有权与生命周期：每个场景首次访问时分配 `grid/ap/va`、材质/色阶数组、`fmCache` 及计数，构建一次并缓存，场景私有闭包也随实例存活；切出不销毁。活动别名和 `matCount/rampCount/staticTop` 是当前场景的暂存副本，build 后及每帧 post 后写回。全局仅有一份动态日志，归属于最后绘制场景，切换前必须激活其数组并逆序撤销，不能误认为每个场景自带日志。`pal`、像素及深度等缓冲、`shifted`、光照和 `state` 是单实例共享；`curAp/curVa` 在首次 build 前后重置，而非每帧重置。保留 `dynMode`、计数和所有场景私有缓存的真实使用时机，不因抽象引入自动清理。

上下文不复制大型 typed array。过渡期可保留原有局部别名和 `saveCounts` 语义；当切换成直接访问场景字段时，必须同步移除旧的标量真值，避免两套状态并存。热循环可保留局部数组引用，不要求每个像素都通过对象链访问。异常路径当前没有事务回滚或重建保证；本次不声称异常后可继续渲染，需在实施前单独决定是否支持及如何测试。

### 4.2 场景契约

场景由显式注册表按现有顺序创建：`seasons`、`rise`、`harbour`、`eruption`、`liftoff`。场景工厂接收受控的构建/渲染 API，返回元数据及 `build`、`update` 和可选 `post` 回调；场景私有的色阶编号、对象列表和关键帧继续由该场景实例持有。

场景 API 按职责提供材料、体素构建、动态覆盖、光照和后处理能力，不允许场景反向导入注册表或渲染器门面。接口的完整方法及精确类型，应以每个场景的实际自由变量梳理结果为准；不可用大面积 `any` 掩盖迁移不完整。

### 4.3 渲染流程约定

迁移前后保持以下顺序：

1. 若目标与上一个场景不同，先激活上一个场景并撤销其动态覆盖；同一场景时跳过此步骤。
2. 对目标场景执行 `ensureBuilt`（必要时构建并激活），然后在当前场景上无条件执行 `undoDyn`；按现有规则初始化本帧状态。
3. 执行场景 update，刷新调色板，渲染体素。
4. 执行场景 post，保存需要持久化的计数器。
5. 应用偏移与淡入淡出，放大画面并绘制画面内 UI，提交 Canvas。

其中 `q = clamp((p - 0.024) / 0.958)`，`T = min(254, floor(q * 255))`，场景接收 `(q, p * 10)`，而淡入淡出和 UI 也使用原始 `p`，不得混用。首次 build 的分配、激活、`curAp/curVa` 重置和计数保存发生在 update 前；缓存命中只激活场景。每帧只重置源码列出的覆盖、风、水、背景混合、抖动、UI、色彩分级和太阳参数；例如 `bgA/bgB`、`coverRamp` 等不应被笼统地全部重置。`post` 在体素渲染之后、计数保存之前，偏移淡出在保存之后，放大和 UI 属于 `main.ts` 的后续调用；背景 DOM 样式在 `putImageData` 之后更新。

不得将动态日志迁走后丢失所属场景；同一体素可被重复记录，必须逆序恢复 `grid/ap/va`。当前 `JCAP=3000000`，达到容量或坐标越界时后续写入直接忽略；本次不改变这些行为。

## 5. 图像与行为回归设计

在拆分前建立原始实现的基线；以浏览器内直接读取 Canvas 像素为最终输出依据，记录固定浏览器版本、视口、设备像素比、场景索引和时间进度。基线和被测结果使用同一环境、尺寸和确定性的场景时间；不要用截图文件字节哈希代替对实际像素的比较。

测试控制入口仅用于测试环境，能够设置场景与进度、按指定操作序列逐帧同步绘制并读取完整 `ImageData.data` RGBA；生产构建不暴露该能力。当前 `startApp` 立即执行且状态位于闭包，现有代码没有注入时钟或测试入口：阶段 A 必须先设计最小测试适配层，在原实现和迁移实现使用同一适配方式，核对不改变调用顺序、缓存与状态，且实际交互测试仍通过真实事件路径。使用可控 `requestAnimationFrame` 时钟并区分首次帧、暂停、拖动与恢复；不能仅直接调用 `renderScene` 冒充完整应用。每条冷启动路径在新页面/全新模块实例中开始；同一路径的中间帧按记录顺序执行，不在每次采样时清空状态。

阶段 A 需先选定并记录自动化工具及版本、浏览器二进制、系统、视口、DPR、采样序列和基线保存位置/体积策略；本项目目前只有 TypeScript 和 Vite，无测试脚本或浏览器自动化依赖。新增工具、脚本和基线是后续实施工作，并非现状。基线必须来自迁移前的冻结版本，独立保存且附生成命令、版本标识和校验信息；不得用迁移后输出重生成来验证自身。比较 RGBA 尺寸和逐通道值，输出差异像素数量、位置及差异图；固定环境期望零差异，不稳定先排查。至少重复采集同一路径两次验证基线稳定性；记录不可复现项并阻止该项验收。

- 每个场景固定采样 `p = 0、0.039、0.04、0.041、0.25、0.5、0.75、0.969、0.97、0.971、0.999`，再根据各场景事件增加明确采样点；测试入口直达帧和真实交互可达帧分别标记，不把 `p=1` 假定为正常播放终点。采集清单记录场景、进度和完整操作路径。
- 对同一目标帧分别从冷启动、同场景向前/向后 seek、其他场景跳入采样；同一路径对比迁移前后的像素，额外记录不同路径可能存在的原始差异，不预设它们必然相同。
- 重点覆盖场景 A→B→A、动态覆盖重复写入和恢复、运行时材质分配、夜景与日景相互切换。增加独立状态测试：重复覆盖同一坐标后逆序恢复三数组、切换时不污染目标、缓存场景不重复 build、运行时分配后的计数及 `fmCache` 跨切换保留、边界/容量写入被忽略。测试应检查状态而非只在淡出全白帧比较像素；容量测试可用小容量注入的等价单元实现配合真实容量边界检查，但不能改变生产容量。
- 比较完整输出（包括场景标题和滑块）；如需定位差异，可额外暴露逻辑像素缓冲进行诊断，不改变生产行为。
- 交互断言：空格切换暂停与播放并阻止默认行为；左右键在首尾场景循环；数字 1–5 分别跳到对应场景起点。播放及暂停两种状态都测试滑块：有效区域按下捕获指针并立即 seek，拖动期间自动时间不推进，但 pointermove 可主动改变时间；释放或取消后结束拖动，原为播放时继续推进、原为暂停时仍暂停，区域外按下不启动拖动。验证坐标映射、轨道两端钳制和 `lerp(0.024, 0.982, position) * 0.999`。开启减少动态效果时启动于首场景第 4 秒且不自动推进，空格仍可播放；不额外承诺运行时设置变化。
- 在 `state.bgMix` 阈值两侧断言 `html` 与 `body` 背景样式（大于 0.55 为 `rgb(14,18,44)`，否则白色）；至少选择两组视口及设备像素比，按 `max(1, floor(min(innerWidth/360, innerHeight/330) * DPR))` 验证内部尺寸、除以 DPR 的 CSS 尺寸以及暂停和播放时 resize 后重绘与基线一致。
- 性能在同一机器、浏览器、视口及固定采样路径下采集：每场景冷启动重复 5 次，稳定帧和高动态帧各预热 30 帧后测量 100 帧，记录中位数与 P95；访问五个场景后测内存并注明 API 及不可用情况。测得基线后先约定容忍区间及复测规则，再开始迁移；未约定前不得宣称性能验收通过。

已有代码是兼容基准，不把测试采集过程中发现的原有缺陷默认为可修复内容；任何修复需要单独记录、确认和更新基线。

## 6. 分阶段迁移与验收

### 阶段 A：建立基线

先确定测试工具、适配方式、基线存储和命令；固定采样与运行环境，建立可重复像素比较和关键交互检查；在现有实现上重复采集确认稳定并保存冻结基线。按第 5 节记录冷启动、帧耗时及可用的内存数据，并在迁移前确定容忍区间和复测规则。若出现路径相关差异，先记录原行为，不以“不同路径必须同图”为通过条件。

### 阶段 B：提取低耦合模块

逐项提取数学与噪声、确定性查表、画面内 UI。UI 显式接收场景数量、背景状态等原先从全局读取的依赖；缩放函数显式接收源像素，兼容门面维持原调用方式。每次提取后运行回归，禁止混入视觉修改。

### 阶段 C：封装单实例状态

引入 context 并保持数组、计数器和动态覆盖的原有生命周期；对场景切换、日志逆序恢复和材质计数增加针对性测试。此阶段不添加并发或多实例承诺。

### 阶段 D：逐场景迁移

明确场景契约及所需 API，从一个场景开始逐个迁移；每迁一个场景运行全部回归矩阵，并验证懒构建、切出切回及原顺序。所有场景迁移后再整理注册表。

### 阶段 E：拆分管线和补齐类型

拆出材质、几何、渲染与后处理职责；保留调用顺序和 typed-array 语义。先对新模块、上下文及场景契约启用严格类型检查，再逐段消除原文件中的 `@ts-nocheck`。不得仅通过整体 `any` 或关闭严格检查满足类型检查。

## 7. 完成标准与回退

- 五个场景在固定环境、固定操作路径和全部基线采样点的最终 Canvas 像素与原实现一致；若存在无法稳定的样本，先解释并解决，不能静默放宽阈值。
- 第 5 节完整交互、背景、尺寸和状态断言均通过；执行 `npm run typecheck`、`npm run build` 和实施时新增的自动化测试命令并记录结果。`tsconfig.json` 的 `strict` 已开启且 `include` 仅为 `src`；新增测试若在 `src` 外须明确独立类型检查配置。渲染核心及迁出的场景/模块不再使用 `@ts-nocheck`、`@ts-ignore` 或通过宽泛 `any` 绕过检查；不能仅凭现有 typecheck 成功证明核心已检查。
- 拆分后的依赖方向与状态归属能从模块接口看清，场景注册顺序与行为不变。
- 使用阶段 A 约定的性能采样、容忍区间与复测规则比较重构前后；超出区间时定位处理或交由用户决策，无法测量的内存指标明确标为未验证。
- 每个迁移阶段独立验证。若回归失败，先定位该阶段差异并回退该阶段的改动，不通过覆盖基线掩盖变化。若项目无 Git，执行前先建立可恢复的版本管理或备份方案，不默认自动提交。

## 8. 审核重点

- 是否以“像素与交互兼容”为优先，接受分阶段推进而非重新设计效果。
- 是否同意渲染器继续保持单实例，不把多画布和并发列入本次范围。
- 是否同意先建立可重复的视觉基线，再按低耦合模块、状态、场景和类型逐步迁移。
- 图像测试使用何种浏览器自动化工具、基线文件如何存放及增加依赖是否获准：实施计划需结合本地依赖和体积评估后明确，不预设现已安装。
- 帧耗时的测量边界（完整 `draw` 或分段）、计时方法、噪声控制、性能容忍区间和复测规则，必须在采集基线并开始迁移前由实施方与用户确定；性能测试不应把自动化截图/像素读取耗时混入帧耗时。
- 事件驱动场景的具体采样点须按各场景关键帧/分支逐一列入清单；当前文档的公共采样只是下限，不是已经完成的覆盖证明。
